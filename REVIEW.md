# Критерии независимого ревью

Проверяй внешнее поведение и соответствие согласованной спецификации, а не число изменённых строк. Прочитай исходное обращение, спецификацию, связанные тикеты, человеческое согласование, diff и доступные результаты CI. Если какой-то источник недоступен, прямо укажи ограничение проверки.

## Календарь и бронирование

- Занятый слот не остаётся доступным для повторной записи.
- Любые пересечения бронирований запрещены, в том числе между разными типами встреч; встреча может начинаться ровно в момент окончания предыдущей.
- Изменение не должно неявно менять формирование слотов, доступность или правила конфликтов.
- Публичная доступность и `busyIntervals` не раскрывают имя, email, заметку гостя или другие приватные детали встречи.
- Существующие сценарии без новых опциональных полей продолжают работать без изменений.

## Заметка гостя

Для изменений по спецификации #4 проверь:

- заметка необязательна на всём пути TypeSpec → OpenAPI → generated SDK → backend → frontend;
- максимальная длина — 500 символов; 501 символ даёт `400 VALIDATION_ERROR` с ошибкой на поле `note`, а не-string значение даёт `400 MALFORMED_REQUEST`;
- backend удаляет пробелы по краям; заметка из одних пробелов считается отсутствующей, сохраняется и возвращается как отсутствующая;
- гость видит сохранённую заметку в подтверждении, владелец — в деталях предстоящей встречи;
- встреча без заметки отображается как раньше; заметка не появляется в календаре, списке или публичных слотах;
- конфликт бронирования с заметкой по-прежнему возвращает `409`;
- основной, негативный и соседние сценарии покрыты тестами на внешних границах приложения;
- сгенерированные файлы не изменены вручную, а изменение выходит за согласованный объём только после явного согласования человеком.

## Результат ревью

Каждое подтверждённое замечание должно содержать:

1. путь к файлу и номер строки в текущем head;
2. условия, при которых возникает ошибка;
3. последствие для пользователя или согласованного поведения;
4. минимальную рекомендацию по проверке исправления.

Не сообщай о предположениях как о подтверждённых дефектах. Учитывай предыдущие замечания и не повторяй уже исправленные или отклонённые человеком пункты без новых оснований. Не дублируй вывод линтера и форматтера. Если подтверждённых дефектов нет, напиши это прямо и перечисли ограничения проверки, если они были.
